# Versioned MIND extensions

MIND evolves through reviewed changes to a programming language. Proposals are **untrusted data**, not executable plugins. This sprint supplies lifecycle and verification infrastructure, not gravity, jumping, a full engine, or autonomous implementation.

## Active release and compatibility

`src/release.ts` is the single language-version authority. It lists implemented/unavailable capabilities, accepted project pins, the browser profile, the stabilized v0.1 core commit, and the compatibility-fixture hash. `conformance/v0.1.json` is the machine-readable compatibility baseline. Candidate evidence records the exact full Git commit SHA, candidate fixture hash, baseline hash, build provenance check, Node version, results, and timestamp. `dist/build-info.json` binds a build to tracked source content and compiled modules; it is generated by `npm run build` and is not committed.

Do not weaken old acceptance fixtures when adding a capability. An intentional incompatible change needs a new version, explicit compatibility decisions, and maintainer review. A feature must have real parser/interpreter semantics and passing positive execution fixtures before its manifest metadata can advertise availability. CI checks every supported capability has passing positive coverage. Data labels alone cannot prove that tests adequately specify a mechanic; maintainers must review semantics and test quality.

## States and trust boundaries

`proposed → candidate → verified → approved → published`

- **proposed**: version-aware design request stored by local CLI or MCP. Required fields: `baseLanguageVersion`, `title`, `motivation`, `syntax`, `semantics`, `tests`, `compatibility`, and unique capability IDs.
- **candidate**: local operator associates an exact 40-character source commit, target version, and copied JSON acceptance fixtures. Replacing a candidate before verification, or retrying a failed candidate, preserves previous candidate/evidence snapshots.
- **verified**: a clean checkout matches the candidate commit; build provenance matches; the immutable compatibility baseline and candidate fixtures pass; every requested capability is implemented and has a positive action fixture. Failure persists evidence and transitions to **failed**. To retry, register a candidate again.
- **approved**: an authorized maintainer signs the exact proposal/candidate/verification/version binding using Ed25519. A different candidate, test set, verification run, or action invalidates the signature.
- **published**: a separate authorized signature records publication, after rechecking approval authorization, the exact clean checkout, and a matching committed active release manifest. This is a local signed lifecycle record. It does **not** upload packages, merge branches, create GitHub releases, or change capability metadata automatically.
- **rejected**: local operator rejects a non-finalized proposal with a reason. Approved/published proposals cannot be rewritten, rejected, or replaced through the workflow.

MCP exposes discovery, validation, submission, and status only. Candidate registration, verification, rejection, approval and publication are deliberately local operator commands. A candidate checkout is executable TypeScript maintained by trusted operators: review it and run untrusted implementations in an isolated environment without secrets before invoking build/verification. Proposal submission and fixture execution never evaluate proposal text, import proposed modules, or spawn commands supplied by proposals. Acceptance actions are a fixed dispatcher (`move` only today).

## Gravity and jumping demonstration

From a clean checkout of the feature commit:

```sh
npm ci --ignore-scripts
npm run build
node dist/src/extensions-cli.js submit extensions/examples/gravity-jumping.json
# Copy the returned proposal ID into PROPOSAL_ID.
PROPOSAL_ID=<returned-uuid>
CANDIDATE_REVISION=$(git rev-parse HEAD)
node dist/src/extensions-cli.js candidate "$PROPOSAL_ID" "$CANDIDATE_REVISION" 0.1.0 extensions/examples/gravity-jumping.tests.json
node dist/src/extensions-cli.js verify "$PROPOSAL_ID"
node dist/src/extensions-cli.js status "$PROPOSAL_ID"
```

The verification command intentionally exits **1** and persists `failed` evidence: the v0.1 compatibility fixtures pass, but `tick`/`jump` actions are unsupported and gravity/jumping remain unavailable. Those JSON actions are draft acceptance contracts, not supported `.mind` syntax. The target version is 0.1.0 to demonstrate the missing behavior against today's implementation; a real implementation must select its intended new release version and update supported-version/compatibility metadata through review.

For a passing infrastructure control, submit `extensions/examples/movement-control.json`, register `conformance/v0.1.json` against the current commit, and verify. This control checks existing semantics, not a new released feature. Tests exercise the complete lifecycle using ephemeral test-only keys; no signing key is enabled in the repository.

## Maintainer authorization (manual, disabled by default)

`extensions/maintainers.json` contains trusted Ed25519 public keys indexed by key ID. It starts empty: **approval and publication are denied**. A maintainer must review and commit public-key policy before registering/verifying an official candidate. Private keys never belong in the repository, proposal store, MCP configuration, or CI logs.

```sh
node dist/src/extensions-cli.js approval-payload "$PROPOSAL_ID" > /tmp/mind-approval-payload.json
# Sign the UTF-8 payload with an authorized offline Ed25519 private key.
# Write {"keyId":"<configured-id>","signature":"<base64-signature>"} to a receipt file.
node dist/src/extensions-cli.js approve "$PROPOSAL_ID" /path/to/approval-receipt.json
node dist/src/extensions-cli.js publication-payload "$PROPOSAL_ID" > /tmp/mind-publication-payload.json
# Review and separately sign the publication payload.
node dist/src/extensions-cli.js publish "$PROPOSAL_ID" /path/to/publication-receipt.json
```

Sign the JSON payload bytes **without the CLI's trailing newline**. For example, an offline Node signer can read the payload, remove its final newline, and call `crypto.sign(null, Buffer.from(payload), privateKey).toString("base64")`. Approval and publication payloads differ by `action` and cannot be interchanged. Revoking a public key also blocks publication of an approval made by that key.

Protect `src/release.ts`, `extensions/maintainers.json`, conformance fixtures, verification code and CI via repository review/branch protection. The repository owner must enable required reviews/checks in GitHub settings; source files cannot enforce those hosting settings. No automatic publishing workflow or paid service is configured.

## Input, persistence and operational limits

- Proposal fields: non-empty strings, at most 8 KiB each; at most 64 KiB of serialized input; 1–16 unique capability IDs.
- Source: at most 65,536 characters. MCP arguments: at most 256 KiB; stdio transport buffer: 512 KiB (oversized frames close the connection).
- Acceptance fixtures: 1–100 fixtures, at most 128 KiB serialized, at most 100 actions each. Negative fixtures assert a literal error substring from parsing; positive fixtures assert the exact initial state and each action result. No JavaScript, regular-expression evaluation, or dynamic action dispatch is accepted.
- Storage: at most 100 proposal records, 256 KiB per record, 5 MiB total, and 32 lifecycle transitions per record. Limits apply to updates and archived candidate evidence as well as new submissions. Operators must archive exhausted records outside the live store manually.
- Records live in `extensions/proposals/<uuid>.json` relative to the operator/MCP working directory, are ignored by Git, use restrictive permissions, and are atomically replaced. Writes hold an exclusive cross-process lock, so competing writers fail closed rather than racing quotas or transitions. An operator must inspect/remove a stale `.lock` after a crashed writer. Reads reject symlinks/non-regular/oversized records; JSON is validated before use.

The local filesystem owner, selected candidate checkout and authorized maintainer policy are trusted. This is a single-owner stdio service, not a multi-tenant remote service or a cryptographic append-only audit log. Signed authorization protects approval/publication intent; local intake and verification records still need owner-managed backups. Older unversioned local proposal files are rejected rather than silently assigned a base version; resubmit them with an explicitly reviewed version. Automatic implementation, sandbox provisioning, public approval APIs and remote artifact publication remain out of scope.
